## 2. 排期原则

1. **依赖驱动，不排日历时间**：只给顺序与前置条件，完成一个验收通过再开下一个（[ACCEPTANCE.md](./ACCEPTANCE.md) 的判定不通过不进入下一任务）。
2. **每个任务必须能独立交付**：有明确的产出物、可单独验收、可单独回退；不允许「做了一半卡在依赖上」。
3. **风险优先**：把不确定性最高的任务尽早做掉，避免它在后期推翻前面的设计。
4. **不预先抽象**：没有第二个消费者的东西不提前拆包 / 分层（这是 [ARCHITECTURE.md](./ARCHITECTURE.md) §11 推迟 P1 的同一条理由）。

| 编号 | 任务 | 对应阶段 | 前置 | 风险 |
|---|---|---|---|---|
| **T0** | 谱面语义与诊断契约修复 | P0 正确性 | — | 高 |

### T3 音乐播放器：音频时钟接管时序

| 项 | 内容 |
|---|---|
| **目标** | 跟吹时能播放伴奏音频，且**滚动位置以音频时钟为准**（当前是本地计时器） |
| **具体行动** | 当前已采用本地平滑推进 + 音频周期校准；补验暂停/seek/重播/变速与起吹留白交接，不预先要求逐帧桥接。使用起点和速度匹配的伴奏，另记录前奏或不同速度素材的限制 |
| **产出物** | `player/` 下的音频时钟实现 + 跟吹页播放控件 |
| **验收** | 见 [ACCEPTANCE.md](./ACCEPTANCE.md) §3 的 T3 表 |
| **风险与退路** | 桥接抖动或耗电不可接受时，退回「本地计时器为主 + 音频仅作伴奏」，**不阻塞后续任务** |
| **状态** | **L1 已完成**（`tsc` / `lint` / `verify` / `expo-doctor` 四门禁全绿）：新增 `player/timeSource.ts`（`createAudioClock`）、`usePlayback` 增加可选 `audioUri`、跟吹页新增「伴奏」入口（运行期选文件、不持久化）。**实现选择**：未走「逐帧写回原生位置」，改用「本地计时器平滑推进 + 300ms 周期校准音频时钟，80ms 容差」，目标是兼顾 T3-2 不抖动与 T3-1 不漂移，尚不能宣称已通过（见 [TECH_DESIGN.md](./TECH_DESIGN.md) §7.2）。**L3（T3-1 / T3-2 / T3-3 / T3-6）待真机补验** |

## 4. 明确不做（本版范围外）

| 项 | 原因 / 触发条件 |
|---|---|
| **Monorepo 化** | 第二个独立消费者确需共享发布/构建边界才评估；同仓库 Web 平台和博客链接不自动触发 |
| **后端 / 云同步** | 自动同步、用户上传共享或服务端计算需求明确后评估；公开曲目展示不必依赖后端 |
| **电脑端与博客展示** | 未来 P3 优先验证 Web 核心流程；博客独立展示不复制算法，桌面壳尚未选定 |
| **实时音频反馈**（P5） | 耗电与流量成本高，且依赖 T5 结论 |
| **Web 版跟吹页** | 当前未完成适配与验收；零高度是问题记录，不是永久平台禁令。未来 Web 验收不能代替 Android 真机 |
| **e2e / 单测框架** | 当前用 `scripts/verify-core.ts` 覆盖纯函数层，成本极低；引入测试框架的收益尚未超过其成本。**触发条件**：纯函数层出现回归 |
| **iOS** | 不在当前范围 |
