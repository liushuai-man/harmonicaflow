## 2. 排期原则

1. **依赖驱动，不排日历时间**：只给顺序与前置条件，完成一个验收通过再开下一个（[ACCEPTANCE.md](./ACCEPTANCE.md) 的判定不通过不进入下一任务）。
2. **每个任务必须能独立交付**：有明确的产出物、可单独验收、可单独回退；不允许「做了一半卡在依赖上」。
3. **风险优先**：把不确定性最高的任务尽早做掉，避免它在后期推翻前面的设计。
4. **不预先抽象**：没有第二个消费者的东西不提前拆包 / 分层（这是 [ARCHITECTURE.md](./ARCHITECTURE.md) §11 推迟 P1 的同一条理由）。

### T3 音乐播放器：音频时钟接管时序

| 项 | 内容 |
|---|---|
| **目标** | 跟吹时能播放伴奏音频，且**滚动位置以音频时钟为准**（当前是本地计时器） |
| **具体行动** | ① 定 `TimeSource` 实现（[TECH_DESIGN.md](./TECH_DESIGN.md) §12.2 已留接口）；② **补齐桥接**：用 `useFrameCallback` 逐帧读原生播放位置并写回 `positionMs.value`（原生进度**不能直接赋值给 Reanimated 共享值**）；③ 处理播放 / 暂停 / seek / 变速；④ 实测回调频率不足导致的抖动，必要时降级为「本地计时器 + 周期性校准」 |
| **产出物** | `player/` 下的音频时钟实现 + 跟吹页播放控件 |
| **验收** | 见 [ACCEPTANCE.md](./ACCEPTANCE.md) §3 的 T3 表 |
| **风险与退路** | 桥接抖动或耗电不可接受时，退回「本地计时器为主 + 音频仅作伴奏」，**不阻塞后续任务** |
| **状态** | **L1 已完成**（`tsc` / `lint` / `verify` / `expo-doctor` 四门禁全绿）：新增 `player/timeSource.ts`（`createAudioClock`）、`usePlayback` 增加可选 `audioUri`、跟吹页新增「伴奏」入口（运行期选文件、不持久化）。**实现选择**：未走「逐帧写回原生位置」，改用「本地计时器平滑推进 + 300ms 周期校准音频时钟，80ms 容差」，同时满足 T3-2 不抖动与 T3-1 不漂移（见 [TECH_DESIGN.md](./TECH_DESIGN.md) §7.2）。**L3（T3-1 / T3-2 / T3-3 / T3-6）待真机补验** |

## 4. 明确不做（本版范围外）

| 项 | 原因 / 触发条件 |
|---|---|
| **Monorepo 化**（`packages/*`） | [ARCHITECTURE.md](./ARCHITECTURE.md) §11：只有一个消费者时收益为零。**由 PC 端真正开写触发** |
| **后端 / 云同步** | 当前纯本地个人使用，后端是加分项不是必需项（[ARCHITECTURE.md](./ARCHITECTURE.md) §4）。**触发条件**：需要多设备同步或曲谱分享 |
| **PC 端（Electron）** | 同上，PC 端是可选增强 |
| **实时音频反馈**（P5） | 耗电与流量成本高，且依赖 T5 结论 |
| **Web 版跟吹页** | 浏览器中容器视口高度恒为 0，时间轴渲染不出。**Web 版仅作展示用途，不作为交付目标** |
| **e2e / 单测框架** | 当前用 `scripts/verify-core.ts` 覆盖纯函数层，成本极低；引入测试框架的收益尚未超过其成本。**触发条件**：纯函数层出现回归 |
| **iOS** | 不在当前范围 |
