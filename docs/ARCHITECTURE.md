# 口琴跟吹助手 HarmonicaFlow — 系统架构方案

- 版本：v0.1.0（草案）
- 日期：2026-10-06
- 状态：待评审，未开工
- 关联文档：[PRD](./PRD.md) · [TECH_DESIGN](./TECH_DESIGN.md) · [AI_SCORING](./AI_SCORING.md)

> 本文回答四个问题：**为什么要加后端、多端怎么分、模块怎么切、AI 层怎么设计**。
>
> **本文不锁定 AI 厂商**：全文按 provider-agnostic 设计，只定义契约与适配器插槽，具体选哪家留到开发阶段。原设想中的 Jev（TypeSafe 的 System One 决策模型）经核实**只接收文本、只返回 Choice / Score / Noul 概率，既不生成自然语言、也不接收音频**，与本项目「实时音频多模态 + 生成点评」的诉求不匹配，**已排除**；其「结构化判定 + 置信度」的思路仅作为可选插槽保留（§7.3）。

## 1. 目标与硬约束

### 1.1 本次要达成的目标

| 编号 | 目标 | 判定标准 |
|---|---|---|
| G1 | 引入后端 | 账号、曲谱云库、跨端同步可用 |
| G2 | 多端适配 | 手机（Android）与 PC（桌面应用）都能完成「导入 → 编配 → 跟吹 → 评测」 |
| G3 | 模块化 + 故障隔离 | **PC 端或后端整体不可用时，移动端全部核心功能照常可用** |
| G4 | AI 由用户自带密钥 | 用户自配 API Key，能接收音频的多模态实时能力 |
| G5 | 提示词与输出契约统一 | 换模型只改措辞，不改结论；同一份评分输入，不同模型产出的点评结构一致 |

### 1.2 硬约束（在既有约束上强化）

| 约束 | 来源 | 对本方案的影响 |
|---|---|---|
| 应用整体保持轻量 | 既有 | 后端是**增强层**而非依赖层；移动端包体不因后端而膨胀 |
| 移动端必须离线可用 | 既有（当前为零后端架构） | 所有核心能力（导入/编配/跟吹/离线评分）不得依赖网络 |
| 不使用 Java；出包走 EAS 云端构建 | 既有 | 后端语言选型排除 JVM 系（Kotlin/Scala/Java） |
| 原生变更必须重新出包 | 既有 | 桌面端与移动端的原生部分各自独立发版 |
| 纯本地数据、无隐私外传的历史承诺 | 既有 | 上云必须**默认关闭**、逐项可选、可导出可删除 |

### 1.3 非目标

- 不做社交、排行、直播、课程体系。
- 不做面向第三方的开放平台 / 插件市场。
- 不承诺 iOS（需要付费开发者账号，仍不在范围）。
- **本期不动代码**，只产出方案；`apps/*`、`services/*` 均为规划中的目录。

## 2. 分层总览

```
┌────────────────────────── 客户端（多端） ──────────────────────────┐
│  apps/mobile          apps/desktop                                 │
│  Expo / RN             Electron + React                            │
│      │                      │                                      │
│      └────────┬─────────────┘                                      │
│               ▼                                                    │
│         packages/core        纯 TS：解析 / 编配 / 音高简谱 /        │
│               │              音高检测 / 对齐 / 评分 / 时序          │
│         packages/contracts   数据与 AI 契约（zod schema，单一来源）  │
│         packages/prompts     提示词注册表 + 版本 + goldenset        │
│         packages/ai          Provider 适配器（BYOK，直连厂商）       │
│         packages/storage     存储抽象（现 docStore 上提）            │
└───────────────┬────────────────────────────────────────────────────┘
                │  可选、可断开（HTTP/JSON + SSE）
                ▼
┌──────────────────── services/api（模块化单体） ────────────────────┐
│  identity │ library │ sync │ prefs │ (可选) ai-gateway │ telemetry  │
│            单一部署单元 · 单库 · 模块间只走接口                      │
└───────────────┬────────────────────────────────────────────────────┘
                ▼
        Postgres + 对象存储（曲谱文件、可选评测音频）
```

**两条关键边界**：

1. **`packages/core` 不 import 任何 React / RN / Expo / Node / Electron 模块**——延续现有 `src/core` 的可验证性，Node 脚本能直接跑。
2. **客户端不 import `services/*` 的代码**——只消费 `contracts` 里的类型；后端改动不得要求客户端同步发版。

## 3. 模块划分与依赖方向

### 3.1 目标结构（Monorepo，npm workspaces）

| 路径 | 内容 | 现在是否已存在 |
|---|---|---|
| `packages/core` | 由现 `src/core` 平移：`parsers/` `arrange` `pitch` `layouts/`，未来加 `audio/pitch` `audio/align` `audio/scoring` | 已有（在 `src/core`） |
| `packages/contracts` | 全部跨端/跨进程数据契约：`Score` `TabNote` `Prefs` `EvalResult`、**AI 输入输出 schema**、API 请求响应 schema | 规划 |
| `packages/prompts` | 提示词注册表（`promptVersion` + 模板 + goldenset） | 规划 |
| `packages/ai` | Provider 适配器接口 + 各厂商实现 + 降级链 | 规划 |
| `packages/storage` | 由现 `src/store/docStore.ts` 上提为存储抽象 | 已有（在 `src/store`） |
| `packages/ui-rn` | 现 `src/ui` `src/theme` `src/player` 中可共享的部分 | 已有（在 `src/ui` 等） |
| `apps/mobile` | 现项目主体（Expo Router 页面） | 已有 |
| `apps/desktop` | Electron 壳 + React 渲染进程 | 规划 |
| `services/api` | 模块化单体后端 | 规划 |

### 3.2 依赖方向（单向，禁止反向）

```
apps/*  ──▶ packages/ui-rn ──▶ packages/storage ──▶ packages/ai ──▶ packages/prompts
   │                                                                      │
   └────────────────▶ packages/core ◀────────────────────────────────────┘
                              ▲
                              │（仅类型/校验函数，无运行时耦合）
                        packages/contracts
```

规则：

- `core` 与 `contracts` 是**叶子**，只依赖外部纯 JS 库（`fast-xml-parser` / `fflate` / `zod`）。
- `storage` 提供 `readText / writeText / readBytes / list / remove`，上层（含未来同步逻辑）不关心数据落在本地还是远端。
- **`apps/mobile` 永不 import `apps/desktop` 与 `services/api` 的源码**。
- 用 ESLint `no-restricted-imports` + `dependency-cruiser` 在 CI 里守边界，不靠自觉。

### 3.3 迁移策略（不推倒重来）

1. 先建 workspace 骨架、把 `src/core` `src/store` 平移到 `packages/*`，`apps/mobile` 保持可独立构建可出包。
2. 每次只搬一个包，搬完即跑 `npx tsc --noEmit` + `npm run verify` + `npx expo-doctor`。
3. 桌面端最后接入，**它不得成为移动端构建的依赖**。

## 4. 故障隔离与降级（"PC 端坏掉，移动端也能用"）

### 4.1 五条隔离原则

| 原则 | 落地手段 |
|---|---|
| **编译期隔离** | `core` / `contracts` 无平台依赖；移动端不引用 Electron、Node 专有 API |
| **运行期隔离** | 移动端不依赖后端进程；后端不可达时全部走本地路径，无阻塞等待 |
| **发布隔离** | 三端独立构建、独立版本号、独立更新渠道（移动端走 EAS Update；桌面端走 Electron 更新） |
| **故障域隔离** | 后端模块化单体，每个模块自带超时 + 熔断；一个模块异常不拖垮其他模块 |
| **数据隔离** | 本地数据是**权威副本**，云端是副本；云端清空不影响本机使用 |

### 4.2 降级矩阵

| 故障 | 移动端表现 | PC 端表现 | 用户可见提示 |
|---|---|---|---|
| 后端整体不可用 | 导入 / 编配 / 跟吹 / 离线评分 / 本地曲库 **全部照常**；同步标记为「待同步」入队 | 同左 | 顶部一条不打断操作的「离线，稍后自动同步」 |
| 单个后端模块不可用（如 `library`） | 该模块功能降级，其余不受影响 | 同左 | 只在该功能入口提示 |
| PC 端应用崩溃 / 未安装 | **无任何影响**（两端不共享运行时） | — | 无 |
| AI 厂商不可达 / 无 Key / 超额 | 回落到规则模板点评 | 同左 | 「AI 点评不可用，已使用离线点评」 |
| AI 返回不符合契约 | 重试一次 → 再失败回落模板点评 | 同左 | 静默回落，不弹错 |
| 实时音频链路中断（二期） | 自动切回「录后评」模式 | 同左 | 明确提示已切换模式 |
| 同步冲突 | 保留两份，由用户选择 | 同左 | 冲突列表 |

> 一句话：**后端与 PC 端都是「加分项」，不是「必需项」。**

## 5. 后端：模块化单体

### 5.1 为什么不是微服务（先给结论）

在 **BYOK** 前提下，AI 流量从客户端直连厂商，**不经过后端**；后端只剩账号、曲库、同步、偏好四类读写型 CRUD。这类负载用微服务承载只有代价、没有收益：

| 微服务会引入 | 谁在付代价 |
|---|---|
| N 套部署 / 配置 / 健康检查 | 一个人维护的项目 |
| 服务发现 + 网关 + 链路追踪 | 需要基础设施与学习成本 |
| 分布式事务与最终一致性 | 同步逻辑复杂度翻倍 |
| CI × N + 多版本兼容矩阵 | 每改一次契约都要全量回归 |
| 网络调用取代函数调用 | 本地调试从「打断点」变成「开三个进程」 |

**决策**：先做**模块化单体（modular monolith）**——按模块边界切分，用**编译期规则强制边界**，把「将来能拆」当作设计约束，而不是现在就拆。

> 若用户明确要求微服务，本节即为需要重估的成本清单；不建议在没有独立扩容/独立发布/多团队需求时引入。

### 5.2 模块清单与边界

| 模块 | 职责 | 拥有的数据 | 对外接口（示例） |
|---|---|---|---|
| `identity` | 匿名设备身份 → 可选绑定邮箱 / 第三方登录；发令牌 | `users` `devices` `sessions` | `POST /auth/device` `POST /auth/link` |
| `library` | 曲谱元数据与文件；内置曲库分发 | `scores` `score_files` | `GET /scores` `POST /scores` `GET /scores/:id/file` |
| `sync` | 变更日志（oplog）push / pull，驱动多端收敛 | `change_log` `cursors` | `POST /sync/push` `GET /sync/pull?since=` |
| `prefs` | 主题、主色、口琴预设、音阶校对表等偏好跨端同步 | `prefs` | `PUT /prefs`（带 `version`） |
| `ai-gateway`（**可选**） | 仅当用户不愿意自己配 Key 时提供的托管通道；做限额与审计 | `ai_usage` | `POST /ai/proxy/*` |
| `telemetry`（**可选**） | 崩溃与匿名统计，默认关闭 | `events` | `POST /events` |

### 5.3 模块间通信规则

1. 模块**各自拥有数据表命名空间**（`identity_users`、`library_scores`…），**禁止跨模块直接查表**。
2. 同步调用只允许走对方**导出的 public 接口**（`src/modules/<name>/public.ts`）。
3. 异步解耦用**进程内事件总线**（内存实现；将来换消息队列时接口不变）。
4. 每个模块有独立超时与熔断阈值，故障不冒泡。
5. 边界靠 lint 规则守：`modules/a` 不得 import `modules/b/internal/*`。

### 5.4 接口风格

- HTTP + JSON，契约由 `packages/contracts` 的 zod schema 单一来源，前后端共享；服务端做入参校验，客户端做响应校验。
- 同步接口用**游标 + 增量**，不用时间戳（时钟不可靠）。
- 所有写操作幂等（客户端生成的 `opId`），便于离线重试。
- 版本化：路径 `/v1`；契约破坏性变更必须新增字段而非改字段。

### 5.5 部署形态

| 项 | 建议 |
|---|---|
| 运行时 | Node LTS + Fastify（或 NestJS，团队熟悉度优先） |
| 数据库 | 单实例 Postgres（模块化 schema 命名空间） |
| 对象存储 | 曲谱原文件（S3 兼容） |
| 打包 | Docker 单镜像，单进程多模块 |
| 托管 | 任一支持容器的平台（Fly.io / Render / Zeabur / 自建） |
| 观测 | 结构化日志 + 健康检查端点 `/healthz`（分模块状态） |

### 5.6 什么时候才拆微服务

同时满足以下**至少两条**再考虑，且一次只拆一个模块：

- 单模块有独立的扩容需求（如 `sync` 写放大远超其他模块）；
- 单模块有独立的发布节奏，且改动频繁触发全量回归；
- 出现多团队并行开发，代码所有权需要物理隔离；
- 单模块的故障必须与其他模块物理隔离（合规/安全要求）；
- 单模块技术栈确实不匹配（例如需要 Go 的高并发长连接）。

## 6. 数据与同步

### 6.1 本地优先（local-first）

- **本机数据是权威副本**，读写永远先落本地，UI 不等待网络。
- 云端是副本，用于多端汇聚与备份，**默认可关闭**。
- 这与既有 `docStore` 抽象一致：上层只调 `readText / writeText`，是否同步由下层决定。

### 6.2 同步模型

| 项 | 设计 |
|---|---|
| 数据单元 | 曲谱（`scoreId` + `contentHash`）、偏好（单文档）、评测历史（追加型） |
| 传输 | 变更日志（oplog）：`{opId, entity, entityId, op, payload, baseVersion, clientTs}` |
| 拉取 | `GET /sync/pull?since=<cursor>` 增量返回，客户端记录游标 |
| 推送 | `POST /sync/push` 批量、幂等；失败入本地队列，指数退避重试 |
| 触发 | 应用启动、切前台、手动「立即同步」；**不做常驻长连接**（省电、省复杂度） |

### 6.3 冲突策略

| 数据类型 | 策略 |
|---|---|
| 曲谱文件 | 内容寻址（`contentHash`），同一 `scoreId` 不同内容 → **保留两份**，让用户选择或改名，绝不静默覆盖 |
| 偏好设置 | 字段级「最后写入胜出」+ `version` 乐观锁 |
| 评测历史 | 只追加不修改，天然无冲突 |
| 删除 | 软删除 + 墓碑记录（保证多端一致删除） |

### 6.4 存储落位

现有 `docStore` 已有原生 `expo-file-system` / Web `localStorage` 两套实现。规划中的第三套实现是 **remote-backed**：本地仍是主存储，远端作为同步目标。**上层业务代码不感知存储位置**——这是既有约定，不在本文改动。

## 7. AI 层

### 7.1 三层拆分（最重要的一节）

```
①  音频理解层   采集 PCM / 片段 ──▶ 转文本或结构化观测
                                    （本地算法 或 多模态模型）
②  判定层       结构化观测 ──▶ 分数、错误点、状态      ← 由【本地算法】完成
③  语言化层     结构化结果 ──▶ 自然语言点评            ← 由【生成式 LLM】完成
```

**铁律**：

1. **分数由本地算法算**（音准音分、节奏毫秒偏差、稳定度、完整度），模型**不参与打分**。
2. 模型只负责把结果「说得像人话」；模型给出的任何数字都**必须被丢弃**，只保留文案。
3. 这样做的直接收益：断网、换模型、模型改版、模型幻觉——**分数都不会变**。这正是「不同 AI 做出一样的效果」的实现基础（见 §9.1）。

### 7.2 BYOK 密钥管理

| 项 | 要求 |
|---|---|
| 存放位置（移动端） | `expo-secure-store`（iOS Keychain / Android Keystore） |
| 存放位置（PC 端） | Electron `safeStorage`（OS 级加密） |
| **绝不** | 写进 `docStore`（会被同步上云）、写进代码库、写进提示词、打进安装包 |
| 传输 | 客户端**直连厂商**；Key 只出现在请求头 |
| UI | 设置页提供「配置 / 测试连通性 / 清除」；明文只显示后 4 位 |
| 合规 | 首次使用前明确告知：密钥与音频将发送至所配置的第三方服务 |

### 7.3 Provider 适配器插槽

```
packages/ai/
  types.ts            # 统一接口，与厂商无关
  providers/
    text/             # 一期：文本 LLM 点评（OpenAI 兼容 / Anthropic / Gemini …）
    realtime-audio/   # 二期：支持音频流的多模态（Gemini Live / OpenAI Realtime / Qwen-Omni / 豆包实时语音 …）
    decision/         # 可选：结构化判定模型（如 Jev 类 Choice/Score/Noul 思路）
  fallback.ts         # 降级链：主厂商 → 备厂商 → 规则模板
```

```ts
interface CommentProvider {
  id: string;
  /** 输入固定契约，输出固定契约；实现方不得修改任何分数 */
  comment(input: EvalInput, opts: { promptVersion: string; signal?: AbortSignal }): Promise<EvalComment>;
}
```

- 一期只落**一个**文本 provider 的实现，其余按需补。
- 适配器**不允许把厂商专有字段泄进调用方**——统一由 `contracts` 里的 schema 表达。
- 新增厂商 = 新增一个文件，不改调用方一行代码。

### 7.4 为什么不做「平台统一 Key」

统一 Key 意味着 AI 流量必须过服务器，需要限流、审计、计费与滥用防护，还要为音频流维持长连接与带宽——这会把后端从「CRUD 单体」逼成「真正的 AI 网关微服务」，成本和隐私面都会显著上升。**保留 `ai-gateway` 作为可选模块**，不做默认路径。

### 7.5 降级链

```
用户配置的 provider
   └─ 超时 / 401 / 429 / 契约不符 ──▶ 重试一次（指数退避）
                                      └─ 仍失败 ──▶ 规则模板点评（离线可用，零成本）
```

规则模板点评见 [AI_SCORING.md](./AI_SCORING.md) §8.1，与 LLM 点评共用同一接口，可无缝降级。

## 8. 实时音频分期路线

| 阶段 | 形态 | 音频路径 | 延迟目标 | 前置条件 |
|---|---|---|---|---|
| **一期** | 录完再评 | 录音文件 → 本地算法 → 结构化结果 → 文本 LLM 包装 | 出分 ≤ 3s（30s 音频） | [AI_SCORING.md](./AI_SCORING.md) 的 **spike-1**（能否拿到 PCM） |
| **二期** | 真·实时 | 实时 PCM 分片 → 多模态模型流式返回 + 本地算法并行 | 反馈 < 500ms | 一期稳定 + 选定支持音频流的 provider |
| **三期**（可选） | 实时教学 | 实时指法/气息建议、逐句循环纠正 | — | 二期数据验证有效后再评估 |

**二期关键设计**：

- 实时链路**只做「语言化反馈」**；音准/节奏判定仍由本地算法做，避免网络抖动影响评分。
- 音频分片以固定窗（如 200ms）推送，本地保留滑动缓冲用于算法。
- 断链自动切回一期模式（见 §4.2 降级矩阵），用户无感。
- 实时链路是**可选开关**，默认关闭——避免流量与耗电劝退离线用户。

## 9. 提示词与契约规范（"不同 AI 做出一样的效果"）

### 9.1 先说清楚：一致性靠契约，不靠提示词措辞

「统一提示词让不同模型结果一致」这句话需要拆开看：

| 诉求 | 能否靠提示词达成 | 真正的解法 |
|---|---|---|
| 分数一致 | ❌ 不可能也不该 | **分数不由模型产生**（§7.1），模型只做措辞 |
| 结论一致（哪些是问题、严重程度排序） | ⚠️ 部分 | **排序由算法给出**，模型只按给定顺序复述 |
| 结构一致（字段、条数、字数） | ✅ 可以 | **输出 JSON schema + 校验 + 重试 + 降级** |
| 风格一致（口吻、人称、长度） | ✅ 可以 | 提示词模板 + 少量示例 + 低温度 |
| 内容一致性可度量 | — | **goldenset + 一致性评测**（§9.5） |

**结论**：把「必须一致的」交给算法与 schema，把「允许差异的」交给模型。提示词只解决风格，schema 解决结构，评分算法解决正确性。

### 9.2 统一输入契约

模型输入是**结构化 JSON**，不含自由文本、不含用户隐私、不含音频（一期）：

```jsonc
{
  "schemaVersion": "eval-input.v1",
  "score": { "total": 78, "grade": "B" },
  "dimensions": { "pitch": 82, "rhythm": 74, "stability": 80, "completeness": 76 },
  "topIssues": [                       // 由算法排序，模型不得重排
    { "noteId": "n_014", "measure": 3, "hole": 6, "action": "draw",
      "status": "off-pitch", "cents": -42, "expectedNote": "A4" },
    { "noteId": "n_032", "measure": 7, "hole": 4, "action": "blow",
      "status": "off-tempo", "timingOffsetMs": 180 }
  ],
  "context": { "title": "小星星", "tempoBpm": 90, "layoutName": "24 孔复音 C 调" }
}
```

- 字段顺序固定、数值单位固定（音分 / 毫秒）、枚举固定（`NoteStatus`）。
- 该 schema 定义在 `packages/contracts`，与 [TECH_DESIGN.md](./TECH_DESIGN.md) §3 的数据模型同源。

### 9.3 统一输出契约

```jsonc
{
  "schemaVersion": "eval-comment.v1",
  "promptVersion": "comment.zh.v1",
  "summary": "整体稳，音准还有空间。",        // ≤ 30 字
  "issues": [                                // 1–2 条，按输入顺序，不得编造
    { "noteRef": "n_014", "text": "第 3 小节 6 孔吸气偏低约 40 音分。" }
  ],
  "advice": "放稳气息，别急着换孔。",          // 1 条，可执行
  "encouragement": "继续加油！"               // ≤ 20 字
}
```

- 严格 JSON、无 Markdown 包裹、无额外字段；条数与字数上限写进 schema。
- 客户端**解析失败即视为失败** → 重试一次 → 回落模板点评。
- 展示层只渲染这些字段，不渲染模型的「自由发挥」。

### 9.4 提示词注册表与版本

| 项 | 规范 |
|---|---|
| 存放 | `packages/prompts/`，随代码版本控制，**不入数据库**（便于 diff / 回滚 / 评审） |
| 命名 | `<用途>.<语言>.v<序号>`，如 `comment.zh.v1`；破坏性改动必须升版本号 |
| 结构 | `system`（角色与禁令）/ `task`（任务描述）/ `outputSchema`（引用 contracts）/ `examples`（少量固定示例）/ `params`（temperature 等） |
| 版本记录 | 每次评测结果记录 `promptVersion` + `providerId` + `modelId`，可追溯到具体组合 |
| 变更纪律 | 改提示词 = 改代码，走同一套提交与评审；**不允许在服务端热改提示词**（会破坏可复现性） |

### 9.5 一致性评测方法（G5 的验收手段）

1. **goldenset**：固定 20–30 条典型输入（全对、单音偏低、节奏抢拍、漏吹多、信号不清晰），每条人工标注「期望结论」。
2. **跑矩阵**：`模型 × promptVersion` 全组合各跑一遍，结果落表。
3. **打分维度**：
   - 结构合规率（能否稳定产出符合 schema 的 JSON）——目标 100%（靠重试 + 降级兜底）；
   - 结论一致率（指出的问题音与 goldenset 标注一致的比例）；
   - 措辞稳定性（同一输入多次调用，`issues[].noteRef` 是否稳定）；
   - 成本与延迟（每次调用 token 与 P95 耗时）。
4. **准入门槛**：结论一致率 < 90% 或结构合规率 < 100% 的模型，不进默认推荐列表（用户仍可手动配置）。
5. 评测脚本放 `scripts/eval-prompts.ts`，与现有 `scripts/verify-core.ts` 同风格（Node 直跑、无 UI）。

### 9.6 硬性禁令（写进 system 提示词与代码双重兜底）

- 不得修改、重算或质疑输入中的任何分数；
- 不得编造输入中不存在的音符、小节、孔位；
- 不得输出 Markdown / 表情 / 多余字段；
- 不得索要或复述用户的 API Key；
- 不得做医疗、听力损伤等专业判断，涉及不适一律建议休息。

## 10. 技术选型 ADR

### ADR-1：后端语言选 **TypeScript**（Node + Fastify/NestJS）

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **TypeScript** | 直接复用 `packages/core` 的解析/编配/音高/评分纯 TS 资产；契约类型两端共享；一个语言维护成本最低；生态与人才充足 | CPU 密集型任务弱于 Go | ✅ **采用** |
| Go | 并发与长连接强、部署单文件 | 与客户端**零代码复用**，音高/评分算法要写第二遍；二语言带来类型割裂与双份 CI | ❌ 暂不采用；将来若 `sync` 或实时音频代理出现真实性能瓶颈，再**单点**引入 |
| Python | AI 生态最好 | 为「调用 HTTP API」引入第二语言不划算；类型系统弱，契约易漂移 | ❌ 不采用 |
| Java/Kotlin | — | 本机不装 JVM，与既有硬约束直接冲突 | ❌ 排除 |

> 关键论据：本项目的算法资产（MusicXML/ABC 解析、束搜索编配、简谱换算、音高检测、评分）**已经在 TS 里跑通并通过自检**。换语言等于把最有价值的资产重写并重新验证一遍。

### ADR-2：后端形态选 **模块化单体**，不选微服务

见 §5.1 成本清单与 §5.6 拆分触发条件。核心判据：BYOK 下后端不承载 AI 流量，只剩 CRUD，微服务无收益。

### ADR-3：PC 端选 **Electron**

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **Electron** | 复用 TS 生态与 `packages/*`；Web 技术栈上手快；音频 API（Web Audio / MediaRecorder）成熟，**利于二期实时音频**；打包成熟 | 包体较大（~100MB 级） | ✅ **采用** |
| Tauri | 包体小、内存低 | 需 Rust 工具链（新增第二语言）；音频采集与跨平台细节更折腾 | ❌ 暂不采用 |
| 纯 Web（PWA） | 零安装 | 无法访问本地文件系统与长期存储的方式受限，麦克风与热键体验受限 | ❌ 作为附带产物可考虑，不作为主形态 |

### ADR-4：客户端与后端协议选 **HTTP + JSON（+ SSE）**

- CRUD 与同步用 HTTP + JSON，游标增量；
- 后端 → 客户端的推送（如有）用 SSE，**不用 WebSocket**（单体场景下 WebSocket 的复杂度和长连接成本不划算）；
- AI 实时音频链路**直连厂商**，与自家后端协议无关。

## 12. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 多端造成维护成本翻倍 | 两端 UI 各写一套 | UI **不强行复用**，只复用 `core` / `contracts` / `ai`；PC 端优先级低于移动端，可延后 |
| 后端成为隐式依赖 | 违背离线可用承诺 | 降级矩阵 + 契约测试（断网跑通全流程作为验收项） |
| BYOK 门槛劝退用户 | 多数用户不配 Key | 规则模板点评永远可用（一期已够用）；Key 配置可跳过 |
| Key 泄露 | 盗刷与信任崩塌 | 系统安全区存储 + 绝不入库/入包 + 明文只显示后 4 位 |
| 厂商 API 变更/下线 | 点评不可用 | 适配器隔离 + 降级链 + 契约测试；只依赖稳定接口 |
| 实时音频耗电与流量 | 用户关闭 | 默认关闭、显式开启、会话级开关 |
| 上传音频的隐私顾虑 | 信任问题 | 默认**不上传音频**（一期只传结构化数值）；如二期需传，逐次显式同意 + 明示去向 |
| 提示词漂移 | 结果不可复现 | `promptVersion` 随代码版本控制 + goldenset 回归 |
| 一次性设计过大 | 永远落不了地 | 严格按 P1→P5 推进，每阶段独立可用、可停 |
