# HarmonicaFlow — UI 设计原则与交付约束

- 版本：v0.1.0
- 日期：2026-10-08
- 状态：设计约束；具体视觉方向、默认数值和真机观感尚未定档。
- 关联：[PRD](./PRD.md) · [技术实现](./TECH_DESIGN.md) · [验收](./ACCEPTANCE.md)

## 1. 设计目标

让用户感到这是一件为口琴练习制作的乐器辅助工具：有辨识度、能长期观看、在演奏时容易读懂。美感、个性与正确性共同构成质量，不用更多设置项代替设计决策。

固定的信息骨架是：**音块表达时机与持续时间，瀑布底部的演奏面板表达孔位与吹吸**。横向模式时面板随判定线移到对应一侧。保持音块、轨道、孔位的一一映射，不因主题、视角或可视窗口变化重新编号。

当前白线和彩色皮肤是已有实现，不代表最终品牌方案。复古、霓虹、木质、唱片等方向均未选定；不因本文件出现“乐器”就自行改成拟物风格。

## 2. 信息优先级与页面分工

| 区域 | 首要任务 | 设计约束 |
|---|---|---|
| 曲库首页 | 找到曲目、导入、开始练习 | 可用口琴图形、封面和排版表达个性；来源格式等技术信息降为辅助信息 |
| 入门学习页 | 选择基础练习、查阅读谱概念 | 用编号、留白和既有卡片建立层次；知识按节展开，明确简谱数字不等于孔号 |
| 基础练习页 | 按当前琴型练音阶与节奏 | 复用瀑布与底部动作锚点；提示简短，缺音明确阻止开始，不用假评分鼓励用户 |
| 跟吹页上方 | 确认曲目、当前琴型和异常 | 封面与标题不得挤压演奏区域；长标题、错误提示出现时布局仍稳定 |
| 瀑布区 | 预判音符到达与持续时间 | 装饰线、透视、光效不得遮挡音块轮廓或误导起止时刻 |
| 底部演奏面板 | 识别当前孔位、吹或吸，必要时推键 | 孔号与动作是主要信息，简谱是辅助；用清晰图例建立动作语义，不强迫追读移动音块 |
| 播放控制 | 播放、暂停、重播、倍速、定位 | 与演奏面板区分；触控区域充足，不与系统手势区域冲突 |
| 设置页 | 找到少量常用偏好与高级调节 | 分组与渐进展开；不把所有开发常量变成用户选项 |

24 孔、小屏、横向模式、系统放大字体必须单独检查。空间不足时先压缩辅助文案和装饰；不可静默隐藏当前动作、任意重排孔位或靠无限缩小文字容纳。新的缩放、局部聚焦等交互需单独设计并验证，不在本轮默认引入。

## 3. 品牌一致性与个性化边界

1. 先设计一套完整、无需调整的默认外观，再提供少量有区别的风格变体。现有偏好继续保留；新增主题预设、恢复默认等能力须在实施任务中明确，不能写成已完成。
2. 个性来自统一的字体层级、留白、口琴图形、音块语言、底部面板与动效节奏。避免每页采用不同圆角、描边、投影或无关装饰。
3. 品牌主色与吹吸、警告、不可吹等语义色分离。皮肤可以改变外观，但不能颠倒吹吸含义。吹吸与推键须有非颜色线索（文字、形状或符号），黑白皮肤也必须可辨。
4. 底部孔位与动作信息不作为可关闭的装饰项。当前动作的强调应明确到吹/吸及推键，不能只亮整列、让两种动作同时看似有效。
5. 不可吹音和解析降级须看得见且含义明确，不以极低透明度隐藏问题，也不使用成功反馈。
6. 新增设置必须说明解决的真实需要、默认值、合法范围、组合风险、持久化与验收方式。无充分理由的视觉细节由设计系统统一决定。

## 4. 动效与状态语义

- 到点高亮表示“现在该吹”，不是“用户吹对了”。未接入并验证录音评测前，不显示伪造的准确率、连击或成功判定。
- 起音提示、持续音状态、结束回落有区别；压线脉冲不能替代持续时间表达。暂停时不继续推进，拖动与重播不产生错误的成批成功反馈。
- 滚动与动作高亮保持在动画线程；低频窗口更新、离散特效节点管理需有边界并实测，不把“用了共享值”当作无卡顿的证明。
- 减少装饰动效的方案应保留时间与动作提示；是否跟随系统及是否提供偏好，随实施方案确定。核心可用性不得依赖粒子、闪烁、悬停或复杂透视。
- 加载、空状态、导入失败、部分解析、不可吹音、伴奏不可读、播放结束均有明确状态；错误不清空已有曲库，不伪装成成功。

## 5. 实现边界

| 内容 | 唯一归属 |
|---|---|
| 时间轴几何、方向、视角约束及相关默认值 | `core/visual/`，纯数据与纯函数 |
| 语义色、皮肤、字体层级、间距、圆角与投影令牌 | `theme/` |
| 基础按钮、行、卡片、图标等通用行为 | `ui/components/` |
| 音块、演奏面板、琴谱与特效 | `ui/` 业务呈现组件 |
| 页面组合、路由与用户操作编排 | `app/`；可复用逻辑移到路由目录之外 |

优先复用现有组件与 SVG 能力，不引第三方 UI/图标库。先在既有令牌体系内实现风格，不为一次改色建立主题插件平台。不同平台共享语义与纯函数；布局密度、输入方式和必要的平台组件允许不同。

## 6. 视觉迭代与交付

1. **记录现状**：同一首曲目、同一播放位置，采集首页、跟吹页、设置页的 Android 截图；播放动画另留短录屏。记设备、系统、构建方式和尺寸。
2. **选视觉方向**：对需要改变整体风格的任务，提供少量可比较的视觉方案；都保留底部信息布局，用户选择后再实现。不能只凭文字宣布已经好看。
3. **统一实现**：先令牌与组件，再页面；不随手修改视觉默认值定档，不用改业务时序弥补视觉问题。
4. **验收**：执行 ACCEPTANCE 的 T1 与 TECH_DESIGN 的 V1–V10，附调整前后证据。可读性、动作含义、触控与状态属于客观要求；风格偏好由用户拍板。

浏览器截图可用于 Web 自身的视觉评审，不能替代 Android 验收。当前 Web 跟吹能力尚未作为完整交付验证；电脑上的静态设计稿也不能证明手机上的动画性能。

## 7. 2026-10-10 跟吹方案定向

用户确认：短促轻柔过渡（按钮120ms、设置180ms）与轻微碎裂（240ms、5片）；底部孔号＋音级＋吹吸、独立当前动作提示；五线谱默认开启，横屏放侧栏；页内设置不中断播放。参数为实现初稿，Android 实拍观感仍待确认。单音窄列音级和动作上下排，不隐藏孔号；多动作琴只强调正在持续的动作，不可吹音无成功反馈。
